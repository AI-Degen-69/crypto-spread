💡 במילים פשוטות: מה התגלה?

דמיינו שאתם מוכרים כרטיסים ותוהים למה לקונים כמעט לא מגיעים (3.6%) בעוד שסימולציה אופטימית מראה 57%. המדידה החוזרת גילתה משהו אחר לגמרי: הכלל המאוחד (שהחליף את המודל הישן) פשוט נותן כרטיס לכל מי שנוגע בדלת — 99.1% מהחלונות מתמלאים. כלומר, הבוט בבק-טסט נראה כאילו הוא מרוויח כל הזמן, בגלל שהסימולציה מניחה שכל זעזוע קטן בספר של 1¢ ממלא את ההזמנה — מה שלא יקרה עם תור אמיתי. הכלי שבנינו מפריד את שני "גלאי המילוי" (הדפסת מסחר מול חדירת ה-ask) ומודד כל אחד בנפרד, בלי לגעת בקוד המנוע.

⚡ איך האימות עובד

01 · בניית מטמון החלונות

‎ev_lab.build_cache‎

כל קובץ ticks נדחס פעם אחת לחלונות ממוזערים (ספרים, טייפ, צדדי מסחר) — אותו מטמון שמעבדת המחקר משתמשת בו, כך שהכלי לא ממציא נתיב משלו.

02 · פירוק הגלאים

עטיפת ‎resting_bid_filled‎

הכלל המשותף נעטף קריאה-בלבד בשני אתרי הקריאה: מצב tape מאלחש את הספר, מצב ask מאלחש את הטייפ ומקפיא ‎newly_placed=False‎, ומצב both הוא הכלל המלא — בלי שינוי קוד במנוע.

03 · ספירה כמו ב-Issue

‎sim2‎ על 550 חלונות

כל חלון רץ בתצורה gates-off, והספירה (רגל-כלשהי / למעלה / למטה / שניים / זוגות) זהה לטבלה שפתחה את #205 — כך שההשוואה הישירה תקפה.

🕹️ מדריך בדיקה ידנית (Touch & See)

הכלי הוא CLI — הנה ההרצה שמייצרת את טבלת המדידה בעיניים:

1. הרצת המדידה בתצורת הכלל המאוחד

python -m research.sweeps.verify_205_fill_rate run/ticks/ticks_2026-09-13.jsonl
מה אמורים לראות: שורת סיכום עם 550 חלונות, ‎any_leg = 545‎ ו-‎99.1%‎ — ההוכחה בעיניים שהכלל המאוחד כמעט תמיד מתמלא.

2. בידוד גלאי הטייפ בלבד

python -m research.sweeps.verify_205_fill_rate --detector tape run/ticks/ticks_2026-09-13.jsonl
מה אמורים לראות: ‎any_leg = 68‎ ו-‎12.4%‎ — אותו מנוע, אותם נתונים, רק גלאי ההדפסות. הפער בין שתי ההרצות הוא כל הסיפור.

3. בידוד גלאי הספר בלבד

python -m research.sweeps.verify_205_fill_rate --detector ask run/ticks/ticks_2026-09-13.jsonl
מה אמורים לראות: שוב ‎545 / 99.1%‎ — זהה למצב המאוחד, ההוכחה שהגלאי הספרי שולט לגמרי בתוצאה.
